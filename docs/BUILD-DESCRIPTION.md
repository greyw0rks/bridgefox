# BridgeFox build description

People who rely on browser extensions can hesitate to switch to Firefox when the tools they need are missing or have limited support. For crypto users, this can mean losing access to a preferred wallet, dApp integration, or security tool. When those extensions prioritize Chrome and other Chromium browsers, users can feel tied to that ecosystem even if they would prefer Firefox. The crypto extension gap becomes a barrier to Firefox adoption.

BridgeFox addresses this barrier by helping developers bring Chrome extension source to Firefox. Its migration studio combines compatibility analysis, migration proposals, source review, and candidate packaging in one workspace. By making extension portability easier to assess and implement, BridgeFox aims to expand the tools available on Firefox and make it a more practical choice for everyday users and crypto users.

Chrome and Firefox both support WebExtensions, but their manifests, background execution models, and API support can differ. BridgeFox helps developers inspect those differences, preserve permissions and assets, and review proposed changes before testing the result.

Developers start by uploading an extension source ZIP or importing a public GitHub branch. BridgeFox preserves source files, binary assets, and licenses, then checks the manifest, declared resources, JavaScript syntax, and individual browser API members against bundled Mozilla compatibility data. The report separates supported features, migration concerns, and issues that require manual review.

The migration workflow offers two paths. Local rules propose conservative changes without an AI account, including a Firefox background script and a stable test identity when the extension is suitable. The Otari workflow adds a compatibility analyst and migration engineer using two distinct open-weight Qwen models, with returned usage, cost reporting, and Python sandbox validation. Developers review each proposal before exporting; patch checks reject permission changes, unsafe paths, and attempts to hide unsupported features by deleting them.

Key features include split and unified source diffs, file search, editor focus, compatibility and permission reports, streamed migration activity, and downloadable Firefox candidates. Larger source repositories can retain TypeScript, build files, and multiple browser manifest templates for review and source export. The hosted studio uses Convex for shared temporary project storage, direct ZIP uploads, and exported downloads. Public local migration is available on the website, while Otari execution requires the workspace password.

The stack is Next.js 16, React 19, TypeScript, and Framer Motion for the studio; Acorn, JSZip, and Mozilla browser compatibility data for analysis and packaging; Convex for project records and files; and Otari for model calls and sandbox validation. Vercel hosts the app. Validation includes automated pipeline tests, Playwright browser checks, web-ext linting, and Firefox checks through geckodriver.

A genuine two-model Otari migration of the original Tab Pocket fixture completed with Python validation and a recorded cost of $0.010456. Its exact exported ZIP passed Firefox checks for saving, persistence, and reopening a tab. Static analysis does not prove runtime compatibility. Source repositories must be built before installation, and wallet migrations require security review and Firefox runtime testing. Permanent distribution follows the usual Mozilla signing process.
